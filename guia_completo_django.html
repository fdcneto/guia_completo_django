🔧Instalação e Configuração do Ambiente

Para evitar conflitos entre projetos, seguiremos o "Caminho Sagrado" do Python: criar uma pasta, isolar o ambiente, e só depois instalar as ferramentas. Siga a ordem exata:

1Criar a Pasta do Projeto

Primeiro, crie o local onde seu projeto vai morar. Evite nomes com espaços ou caracteres especiais.

Terminal/PowerShell 
mkdir meu-projeto-django
cd meu-projeto-django

2Criar o Ambiente Virtual (Venv)

O comando abaixo cria uma pasta chamada .venv que conterá uma instalação isolada do Python. Isso evita que o Django desse projeto interfira em outros.

Terminal 
python -m venv .venv
💡 Dica: Se o comando acima der erro dizendo que "python não foi encontrado", tente usar python3 -m venv .venv ou verifique se instalou o Python marcando a opção "Add to PATH".

3Ativar o Ambiente Virtual

Esta é a etapa onde a maioria dos erros acontece. Você precisa "entrar" na pasta criada. Observe se aparecerá um (.venv) verde no início da linha do terminal.

Windows (PowerShell) 
.\.venv\Scripts\Activate
Linux/macOS (Bash) 
source .venv/bin/activate
⚠️ Erro Comum no Windows:

Se aparecer um erro vermelho dizendo "a execução de scripts foi desabilitada neste sistema", é uma trava de segurança do Windows. Para corrigir, execute este comando e tente ativar novamente:

Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

(Isso libera a execução apenas para essa janela do terminal, sem comprometer a segurança global do PC).

4Instalar o Django

Agora que o ambiente está ativo (tem o (.venv) no terminal?), podemos instalar o Django com segurança.

Terminal (com venv ativo) 
pip install django

Para verificar se instalou corretamente e ver a versão:

python -m django --version

5Instalar Dependências Extras

Instale outras bibliotecas que seu projeto vá usar. Se for criar uma API, por exemplo:

Terminal 
pip install djangorestframework django-cors-headers python-dotenv
💡 Nota: Sempre instale as bibliotecas com o ambiente virtual ativado. Se fechar o terminal, lembre-se de fazer o Passo 3 novamente antes de instalar qualquer coisa.

6Criar requirements.txt

Para garantir que você (ou outro desenvolvedor) consiga reinstalar tudo isso no futuro com um comando só, "congelamos" as versões atuais.

Terminal 
pip freeze > requirements.txt
✅ Conferência: Abra o arquivo requirements.txt que foi criado. Ele deve listar Django==5.x.x e as outras bibliotecas.

3.1📦 Por que usar requirements.txt?

O que é requirements.txt?

É um arquivo que lista TODAS as bibliotecas Python que seu projeto precisa para funcionar, com suas versões específicas.

Exemplo do conteúdo:

Django==4.2.7
djangorestframework==3.14.0
django-cors-headers==4.3.1
python-dotenv==1.0.0
Pillow==10.0.1

🚀 Para Desenvolvimento

Ambientes consistentes: Garante que todos os desenvolvedores do projeto usem as mesmas versões das bibliotecas.

Evita "funciona na minha máquina": Elimina problemas de versões diferentes entre ambientes.

🌐 Para Produção

Deploy consistente: Servidores de produção instalam exatamente as mesmas versões do desenvolvimento.

Reprodução de ambientes: Qualquer pessoa pode recriar exatamente o mesmo ambiente do projeto.

📋 Casos de Uso Práticos:

1. Novo desenvolvedor entra no projeto:

# 1. Clona o repositório
git clone projeto-django
cd projeto-django

# 2. Cria ambiente virtual
python -m venv venv
source venv/bin/activate  # ou .\venv\Scripts\activate no Windows

# 3. Instala TODAS as dependências exatas
pip install -r requirements.txt

# 4. Pronto! Ambiente idêntico ao dos outros devs

2. Deploy em servidor:

# No servidor de produção
git pull origin main
pip install -r requirements.txt
python manage.py migrate
python manage.py collectstatic

3. Problema de versão? Volte no tempo!

# Se uma nova versão quebra seu projeto
# Volte para o requirements.txt do commit anterior
git checkout HEAD~1 -- requirements.txt
pip install -r requirements.txt

⚠️ O que acontece SEM requirements.txt:

  • "Na minha máquina funciona!" - Clássico problema de versões diferentes
  • Quebras inesperadas - Atualização de biblioteca quebra funcionalidades
  • Tempo perdido - Horas debugando problemas de ambiente
  • Deploy falho - Servidor com versões incompatíveis

🎯 Boas Práticas:

  • Sempre gere requirements.txt após instalar novas dependências
  • Commit requirements.txt no Git - É parte essencial do projeto
  • Use versões específicas - Evita "Django" (pega última versão), use "Django==4.2.7"
  • Atualize regularmente - Mas com testes! Não atualize em produção direto

🔐 Segurança Crítica: O Cofre (.env) - Protegendo Seus Segredos

🚨 O Conceito CRÍTICO: Seu código (GitHub) é público, mas suas senhas são PRIVADAS. Nunca salve senhas no código. Use variáveis de ambiente.

Analogia: Imagine dar as chaves da sua casa para um estranho. O .env é seu cofre seguro onde guarda essas chaves!

🎯 Por que isso é TÃO importante?
⚠️ Risco de Hackers

Senhas no GitHub = Convite para ataques. Hackers vasculham repositórios públicos diariamente.

💸 Custos Financeiros

AWS/Banco de dados comprometidos podem gerar custos astronômicos.

🔒 Proteção Legal

Dados de usuários vazados = Problemas legais graves (LGPD/GDPR).

Esta biblioteca é o segurança que controla quem acessa suas variáveis:

Crie um arquivo chamado .env na raiz do projeto (mesmo nível do manage.py):

# 🗄️ BANCO DE DADOS

DB_PASSWORD=senha_super_forte_123!

# 📧 CONFIGURAÇÕES DE EMAIL

EMAIL_PORT=587
EMAIL_USER=meuemail@gmail.com
EMAIL_PASSWORD=senha_do_app_gmail

# 🌐 API EXTERNAS
STRIPE_SECRET_KEY=sk_test_...
GOOGLE_MAPS_API_KEY=AIzaSyB...
AWS_ACCESS_KEY_ID=AKIA...
🚨 CRÍTICO - AÇÃO IMEDIATA REQUERIDA:

Adicione .env ao seu arquivo .gitignore AGORA MESMO!

# No arquivo .gitignore, adicione:
.env
*.env
.env.local
.env.production

Verificação: Execute git status - o .env NÃO deve aparecer na lista!

⚙️ Passo C: Configurar settings.py - Conectando o Cofre

No topo do seu settings.py, adicione:

import os
from dotenv import load_dotenv

# 🗝️ Carrega as variáveis do cofre .env
load_dotenv()

# 🔐 SEGURANÇA - Substitua a chave fixa
SECRET_KEY = os.getenv('SECRET_KEY', 'chave-fallback-caso-erro')

# 🎯 CONFIGURAÇÕES DINÂMICAS
DEBUG = os.getenv('DEBUG', 'False') == 'True'

# 🗄️ BANCO DE DADOS SEGURO
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.postgresql',
        'NAME': os.getenv('DB_NAME', 'meu_banco'),
        'USER': os.getenv('DB_USER', ''),
        'PASSWORD': os.getenv('DB_PASSWORD', ''),
        'HOST': os.getenv('DB_HOST', 'localhost'),
        'PORT': os.getenv('DB_PORT', '5432'),
    }
}

# 📧 EMAIL SEGURO
EMAIL_BACKEND = 'django.core.mail.backends.smtp.EmailBackend'
EMAIL_HOST = os.getenv('EMAIL_HOST')
EMAIL_PORT = int(os.getenv('EMAIL_PORT', 587))
EMAIL_USE_TLS = True
EMAIL_HOST_USER = os.getenv('EMAIL_USER')
EMAIL_HOST_PASSWORD = os.getenv('EMAIL_PASSWORD')
🔧 Boa Prática: Sempre forneça um valor padrão com os.getenv('VARIAVEL', 'valor_padrao') para evitar erros se a variável não existir.

⚖️Django vs Flask: Comparação Completa

🏗️ Entendendo as Diferenças

Django e Flask são dois frameworks Python populares, mas com filosofias diferentes:

  • Flask é como uma casa em construção: você começa com o terreno vazio e escolhe cada material
  • Django é como uma casa pré-fabricada: já vem com estrutura pronta e regras definidas
Característica Flask Django
Tipo de framework Microframework Framework completo
Filosofia "Escolha o que quiser usar" - liberdade total "Baterias incluídas" - quase tudo pronto
Complexidade inicial Leve e simples para projetos pequenos Estrutura robusta, ideal para sistemas grandes
Controle do desenvolvedor Mais liberdade para decisões Mais opinião e padronização
ORM SQLAlchemy ou outro à escolha ORM nativo integrado
Painel administrativo Não possui por padrão Painel admin automático incluso
Arquitetura Manual, o programador define tudo Estruturada em apps independentes
Filosofia de Views Rota decorada na função Rotas e Views separadas em arquivos

4Comparação de Estrutura

Flask (Microframework):

projeto_flask/
├── app.py              # Tudo em um arquivo inicialmente
├── models.py           # Se você criar
├── requirements.txt
└── templates/          # Se você criar

Django (Full-Stack Framework):

projeto_django/
├── manage.py           # Comandos administrativos
├── meu_projeto/        # Configurações do projeto
│   ├── settings.py     # TUDO de configuração
│   ├── urls.py         # URLs principais
│   └── wsgi.py
├── usuarios/           # App específico
│   ├── models.py       # Models do app
│   ├── views.py        # Views (rotas)
│   ├── urls.py         # URLs do app
│   ├── admin.py        # Django Admin
│   └── migrations/     # Versionamento do BD
└── db.sqlite3

5Apps vs Projetos no Django

No Django, existe a ideia de App e Projeto:

  • Projeto: Container de todos os apps + configurações globais
  • App: Módulo específico com funcionalidade única
💡 Exemplo Prático:

PROJETO = Shopping Interior (geovannis_pizza)

  • APP 1 = Loja de Pizza (usuarios)
  • APP 2 = Loja de Bebidas (produtos)
  • APP 3 = Delivery (futuramente)

6Comparação de Arquitetura

Django (MTV) Flask (MVC)
Model (models.py) Model (models.py)
Template (HTML) View (HTML)
View (views.py) Controller (routes)
⚠️ Atenção: No Django, "View" é o que seria "Controller" em outros frameworks!

📖Entendendo a Sintaxe do Django

Django não é uma linguagem, mas possui algumas "mini-sintaxes" próprias além do Python padrão. Vamos entender cada uma:

1. Python (Base de Tudo)

Toda lógica do Django é feita em Python: models, views, urls, admin, migrations.

class Post(models.Model):
    title = models.CharField(max_length=200)
    created_at = models.DateTimeField(auto_now_add=True)

2. Django Template Language (DTL)

Dentro do HTML, Django usa marcas especiais para lógica simples:

<!-- Exibir variáveis com {{ }} -->
<h1>{{ post.title }}</h1>

<!-- Comandos com {% %} -->
{% for post in posts %}
    <li>{{ post.title }}</li>
{% endfor %}
  • {{ }} - Exibe variáveis e expressões
  • {% %} - Executa comandos (for, if, load, block)

3. Sintaxe das URLs

URLs usam uma sintaxe para capturar variáveis da rota:

path("posts/<int:id>/", views.post_detail)
path("user/<str:username>/", views.user_profile)

4. Django ORM (Consultas ao Banco)

Consultas usando API Python ao invés de SQL direto:

# Buscar todos os posts
Post.objects.all()

# Filtrar posts
Post.objects.filter(title__icontains="django")

# Buscar um único objeto
Post.objects.get(id=1)

🗄️Models e Banco de Dados

Models são classes Python que definem a estrutura dos dados. Django converte automaticamente em tabelas SQL.

13O que é ORM?

ORM (Object-Relational Mapping) = Tradução entre Objetos Python e Tabelas SQL.

Sem ORM (SQL puro):

cursor.execute("INSERT INTO usuarios (nome, email) VALUES (?, ?)", 
    ("CoquinhaZero", "coquinha0@email.com"))

Com ORM (Django):

Usuario.objects.create(nome="CoquinhaZero", email="coquinha0@email.com")

14Comparação: Flask vs Django ORM

Flask + SQLAlchemy:

from flask_sqlalchemy import SQLAlchemy
from datetime import datetime, timezone

db = SQLAlchemy()

class Usuario(db.Model):
    __tablename__ = 'usuarios'
    
    id = db.Column(db.Integer, primary_key=True, autoincrement=True)
    nome = db.Column(db.String(80), nullable=False)
    email = db.Column(db.String(80), unique=True, nullable=False)
    senha = db.Column(db.String(255), nullable=False)
    criado = db.Column(db.DateTime, default=datetime.now(timezone.utc))

Django ORM:

from django.db import models

class Usuario(models.Model):
    # id é criado automaticamente pelo Django
    nome = models.CharField(max_length=80)
    email = models.EmailField(unique=True)
    senha = models.CharField(max_length=255)
    criado = models.DateTimeField(auto_now_add=True)
    
    class Meta:
        db_table = 'usuarios'
💡 Diferenças importantes:
  • Django cria id automaticamente
  • EmailField já valida email
  • auto_now_add=True = preenche automaticamente na criação
  • Não precisa inicializar db.init_app()

15Definir um Model

No arquivo blog/models.py:

from django.db import models

class Post(models.Model):
    title = models.CharField(max_length=200)
    content = models.TextField()
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)
    
    def __str__(self):
        return self.title
    
    class Meta:
        ordering = ['-created_at']
💡 Tipos de campos comuns:
  • CharField - Texto curto
  • TextField - Texto longo
  • IntegerField - Números inteiros
  • DateTimeField - Data e hora
  • BooleanField - Verdadeiro/Falso
  • ForeignKey - Relacionamento
  • EmailField - Email com validação

🔎Consultas Avançadas (Lookups)

Operadores de Filtro

O Django permite realizar consultas complexas usando "Lookups" adicionados ao nome do campo com dois sublinhados (__). Exemplos extraídos da documentação:

Comparação de Texto

# Exato (case-sensitive)
Usuario.objects.filter(nome='João')

# Exato (case-insensitive)
Usuario.objects.filter(nome__iexact='joão')

# Contém (LIKE '%jo%')
Usuario.objects.filter(nome__contains='jo')

# Começa com
Usuario.objects.filter(nome__startswith='J')

# Termina com
Usuario.objects.filter(nome__endswith='Silva')

Comparação Numérica e Lógica

# Maior que (Greater Than)
Usuario.objects.filter(id__gt=10)

# Menor que (Lower Than)
Usuario.objects.filter(id__lt=100)

# Entre valores (Range)
Usuario.objects.filter(id__range=(10, 20))

# Está na lista (IN)
Usuario.objects.filter(id__in=[1, 2, 3])

🔄Migrations: Controle de Versão do Banco

📊 O que são Migrations?

Migrations são como "versões" do banco de dados:

  • Migration 0001: Criar tabela usuários
  • Migration 0002: Adicionar campo telefone
  • Migration 0003: Remover campo telefone

TL;DR: Migrations são para o banco o que o Git é para o código.

16Por que usar Migrations?

1. Trabalho em equipe (todo mundo tem o mesmo banco)

Sem migrations: Cada dev teria que criar/alterar tabelas na mão

Com migrations: Django gera arquivos de alteração que podem ser compartilhados

2. Histórico de mudanças

Guarda quando colunas foram criadas, renomeadas ou removidas

3. Reverter alterações se necessário

Cada migração pode ser "desfeita":

python manage.py migrate app 0002

Volta o banco para o estado da migration 0002

4. Deploy facilitado

Quando você sobe o projeto para produção:

git pull
python manage.py migrate

O banco de produção se atualiza sozinho

17Criar e Aplicar Migrations

Migrations são como "controle de versão" do banco de dados:

Gerar migrations 
python manage.py makemigrations

Ou para um app específico:

python manage.py makemigrations blog
Aplicar ao banco 
python manage.py migrate

Ou para um app específico:

python manage.py migrate blog
Django criou as tabelas no banco automaticamente! 🎉
💡 Onde ficam as migrations?

As migrations ficam em app/migrations/. São arquivos Python que representam operações SQL. Django gera automaticamente - nunca edite manualmente (a não ser que saiba o que está fazendo).

🎨Views e URLs

Views são funções (Function-Based Views) ou classes que recebem requisições HTTP e retornam respostas. Elas são o ponto central da lógica de cada rota.

20Anatomia da Request e View

Toda view recebe obrigatoriamente um objeto request como primeiro argumento. Ele contém tudo sobre a requisição:

Atributo Descrição
request.method Método HTTP utilizado (GET, POST, PUT, DELETE).
request.GET Dados passados na URL (Query Parameters). Ex: ?nome=valor.
request.POST Dados enviados via formulário HTML.
request.user Objeto do usuário atual (se autenticado) ou AnonymousUser.
request.body Corpo bruto da requisição (útil para JSON/APIs).

No arquivo blog/views.py:

from django.shortcuts import render, get_object_or_404
from django.http import HttpResponse
from .models import Post

def lista_posts(request):
    # Lógica da view...
    posts = Post.objects.all()
    return render(request, 'blog/lista_posts.html', {'posts': posts})

21Sistema de URLs e Parâmetros

O Django permite capturar partes da URL e enviá-las como argumentos para a view usando conversores (Path Converters).

Tipos de Conversores de URL

  • <int:id>: Aceita apenas inteiros (ex: /produtos/10/).
  • <str:nome>: Aceita qualquer string, exceto o separador /.
  • <slug:slug>: Aceita letras, números, hífens e underscores (ex: /posts/meu-primeiro-post/).
  • <uuid:id>: Aceita identificadores únicos universais (UUID).
  • <path:caminho>: Captura tudo, incluindo barras / (ex: arquivos aninhados).
Query Parameters (GET):

Parâmetros opcionais como /buscar?cidade=rio&idade=20 não precisam ser definidos no urls.py Você os acessa direto na view:

def buscar(request):
    cidade = request.GET.get("cidade") # Retorna None se não existir
    return HttpResponse(f"Buscando cidade: {cidade}")

📝Formulários

Métodos HTTP: GET vs POST

No Django, a mesma URL e View frequentemente lidam com exibir o formulário (GET) e processar os dados (POST). É fundamental checar o request.method.

  • GET: Usado para consultar/exibir. Dados visíveis na URL.
  • POST: Usado para enviar/criar. Dados no corpo da requisição. Requer CSRF Token.

30View para Criar Post (Lógica GET/POST)

from django.shortcuts import render, redirect
from .forms import PostForm

def criar_post(request):
    # Se o usuário enviou dados (clicou em Salvar) - POST
    if request.method == 'POST':
        form = PostForm(request.POST)
        if form.is_valid():
            form.save()
            return redirect('lista_posts')
            
    # Se o usuário está apenas acessando a página - GET
    else:
        form = PostForm() # Formulário vazio
        
    return render(request, 'blog/criar_post.html', {'form': form})

def editar_post(request, pk):

from django.contrib.auth import authenticate, login
from django.shortcuts import render, redirect
from django.contrib import messages

def custom_login(request):
    if request.method == 'POST':
        username = request.POST.get('username')
        password = request.POST.get('password')
        user = authenticate(request, username=username, password=password)
        if user is not None:
            login(request, user)
            return redirect('lista_posts')
        else:
            messages.error(request, 'Usuário ou senha inválidos.')
    return render(request, 'account/login.html')

🎓Conceitos Importantes

MTV Architecture

  • Model: Estrutura dos dados (ORM)
  • Template: Interface visual (HTML)
  • View: Lógica de negócios

ORM (Object-Relational Mapping)

Sistema que converte classes Python em tabelas SQL automaticamente, permitindo trabalhar com banco de dados usando Python puro.

Migrations

Sistema de controle de versão do banco de dados. Cada mudança nos models gera uma migration que pode ser aplicada ou revertida.

QuerySets

Objetos que representam consultas ao banco. São lazy (só executam quando necessário) e podem ser encadeados.

Middleware

Camada de processamento entre requisição e resposta. Usado para autenticação, CSRF, sessões, etc.

Context Processors

Funções que adicionam variáveis automaticamente a todos os templates.

⚠️Erros Comuns e Soluções

Template não encontrado?

Verifique TEMPLATES[0]['DIRS'] no settings.py e certifique-se que a pasta templates/ existe.

Erro 500 no terminal?

Leia o traceback completo - ele indica exatamente qual arquivo e linha está com problema.

Migrations não aplicam?

Execute python manage.py showmigrations para ver o status. Se houver conflito, use python manage.py migrate --fake com cuidado.

Static files não aparecem?

Em desenvolvimento, verifique se django.contrib.staticfiles está em INSTALLED_APPS e use {% load static %} nos templates.

CSRF verification failed?

Certifique-se de incluir {% csrf_token %} em todos os formulários POST.
